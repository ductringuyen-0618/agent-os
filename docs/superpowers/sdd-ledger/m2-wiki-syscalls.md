- Task 3 (WikiService): implementer DONE on branch m2-t3-wikiservice (base 4d94e83), commit faff15c — replaces the M1 stub `wikiService.ts` (same constructor/method signatures, drop-in; `kernel.ts`/`api/server.ts` untouched) with the real implementation. Review found a **Critical, empirically-exploitable** path-traversal vulnerability: `writePage`/`readPage` joined the caller-supplied path onto `wiki/` via `path.join`, which silently collapses `..` segments — a path like `../raw/x.md` skipped the literal `raw/`-prefix check (it doesn't start with `"raw/"`) and `path.join` resolved it right back into the immutable `raw/` directory, **overwriting a raw file**; `../../../../etc/x.md` escaped `osRoot` entirely. Reviewer demonstrated both exploits directly against the running code before any fix. Also **Important**: frontmatter/`links` fields were never secret-scanned (only `content` was), so a secret hidden in a `links` entry would be written verbatim into the page and `index.md`. Ruling: fixed directly (commit 60bff83) with a `resolveWikiPath()` helper used by both `writePage` and `readPage` — resolves the full path via `path.resolve` and verifies containment under a resolved `wikiDir()` (`full === wikiDirResolved || full.startsWith(wikiDirResolved + path.sep)` — the `+ path.sep` specifically closes the sibling-directory-prefix bypass class, e.g. `/os/wiki-evil` being mistaken for inside `/os/wiki`), kept the literal `raw/`-prefix check for its clearer error message, and widened secret-scanning to `[content, ...links].join('\n')`. Added 4 regression tests. A dedicated adversarial re-review (throwaway exploit tests: traversal into raw/, traversal fully outside osRoot, absolute-path injection, backslash-encoded traversal, sibling-prefix bypass attempt, edge cases `.`/`''`) confirmed the fix closes the hole with no new bypass and no regressions (67/67 kernel tests, `tsc --noEmit` clean, no public signature changes). — Why `path.resolve`-based containment over a smarter path-sanitizing library: this is the exact pattern Node's own docs recommend for this class of bug, needs no new dependency, and is easy to audit. — Cost if wrong: none identified; two independent adversarial reviews (implementer's own review + the fix's re-review) tried to break it and couldn't. Minor deferred (not fixed, lower stakes): `listUnindexedRaw`'s "is it indexed" check is a raw substring test against all of `index.md` (`!indexMd.includes(f)`) rather than checking the path appears specifically as a `sources:` reference — a raw filename mentioned in unrelated prose would cause a false "already indexed" and skip it from the unindexed list. Complete (commits 4d94e83..faff15c + 60bff83, review found 1 Critical + 1 Important fixed, both re-verified); merged into m1-kernel-core.

- Task 6 (Run tokens + `/internal/syscall` route): implementer DONE on branch m2-t6-internalroute (base b8684e1), commit 4c43f53. Modified two already-merged files (`eventLog.ts`: added `createRunToken`/`getRunByToken`, reusing the existing `rowToRun` module function; `api/server.ts`: widened the `buildServer` destructuring to include `wiki`/`scheduler` and registered `registerInternalRoutes`) plus new `api/internal.ts`/`internal.test.ts`/`eventLog.runtoken.test.ts`. Review found a **Critical** bug the plan's own TDD script never exercised: M1's `onRequest` hook that enforces `cfg.authToken` as a Bearer header is global (`app.addHook`, not scoped under `/api`), so it 401'd every `/internal/syscall` request whenever a daemon `authToken` was configured — **before** `internal.ts`'s own `X-Run-Token` check ever ran. In any secured deployment (the normal production posture) this broke the entire M2 syscall mechanism end-to-end: every `get_context`/`remember`/`read_wiki`/etc. call from a sandboxed agent subprocess would 401, since those subprocesses are only ever handed a per-run `X-Run-Token`, never the daemon's admin bearer secret (by design — handing out the admin secret to every run would defeat the point of per-run tokens). Reviewer verified this empirically. No existing test caught it: `internal.test.ts` never sets `authToken`, and `server.test.ts`'s bearer-token test never touches `/internal/syscall`. Ruling: fixed directly (commit 23a92c3) — added `if (req.url === '/internal/syscall') return` to the hook, alongside the existing `/api/health` exemption, with a comment explaining why this route intentionally uses a different auth mechanism. Added a regression test exercising both directions (valid run token succeeds with no `Authorization` header even when `authToken` is set; missing/invalid run token still 401s via `internal.ts`'s own check, not the bearer hook). Verified independently (not just implementer's claim) with a full `pnpm --filter @agentos/kernel test` (88/88), `tsc --noEmit` (clean), full root `pnpm -r build`/`pnpm -r test`/`pnpm lint` (all green) before merging — skipped a second dedicated re-review round given the fix is small (one added line + one new regression test that directly exercises the exact reported scenario) and thoroughly self-verified, to conserve the fire's remaining time budget. — Why the exemption is safe: `/internal/syscall` has its own independent auth (the per-run token, validated via `getRunByToken`), so it doesn't need the daemon's admin bearer token too — the two are different trust boundaries (admin operator vs. one sandboxed run) and conflating them would either break the syscall mechanism (as found) or require distributing the admin secret into every sandbox (a worse security posture). — Cost if wrong: would need to scope the hook differently (e.g. an `/api` prefix plugin) — no data at stake, purely routing logic. Complete (commits b8684e1..4c43f53 + 23a92c3, review found 1 Critical fixed); merged into m1-kernel-core.
